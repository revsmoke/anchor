# SPEC: Anchor

- Status: Draft v0.1
- Date: 2026-04-24
- Source: `PRD.md` draft v0.1 dated 2026-04-22
- Product: Web-first, installable DBT daily-structure companion
- Required frontend stack: HTML5, CSS, Vanilla JavaScript
- Required backend stack: Bun, JavaScript, PostgreSQL
- Required methodology: vertical slice / walking skeleton development
- Required coordination artifact: `vertical-slice-dashboard.html` plus its JSON state model

## 1. Purpose

This document translates `PRD.md` into an implementation-ready technical specification for Anchor. It is intentionally detailed enough for multiple agents to build from without drifting into horizontal, layer-first work.

Anchor is a DBT-centered daily structure application. It helps users start, reset, and close their day; log DBT-relevant information; choose practical skills; prepare for therapy; and access safety routing when risk is elevated. Anchor is not therapy, diagnosis, medication guidance, or emergency care.

The primary technical goal is to produce a mobile-first installable web application that remains runnable and browser-testable after every development pass.

## 2. Non-Negotiable Product Constraints

1. Anchor must always preserve the product boundary: DBT practice support, not therapy or emergency care.
2. Safety escalation must interrupt normal coaching when risk signals cross thresholds.
3. Logging must lead to action. Diary cards, check-ins, and chain analyses must generate a next step, recommendation, review item, or exportable insight.
4. The app must support fast use windows: under 30 seconds, about 2 minutes, and about 10 minutes.
5. All persistent sensitive user data must be application-owned structured data, not uncontrolled transcript replay.
6. Raw voice audio must not be retained after the live session except transient runtime buffering.
7. Live transcripts must not be persisted by default.
8. All clinician-facing summaries must be generated from stable data fields plus explicitly selected chain-analysis summaries.
9. The system must be timezone aware and daylight-saving safe.
10. Every primary screen must define loading, first-use empty, returning, offline, error, and safety-interrupted states where relevant.

## 3. Technical Scope

### 3.1 In Scope for V1

- Responsive installable PWA.
- Account creation or anonymous trial shell, depending on final business decision.
- Safety and consent onboarding.
- Daily anchors: morning, midday, evening.
- Today command center with next best step.
- Quick Check-In under 30 seconds.
- Full Diary Card under 2 minutes for most users.
- DBT skills library and guided skill exercises.
- Text coaching with specialist agent orchestration.
- Live voice coaching with browser Realtime session.
- Day reset and minimum viable day mode.
- Chain analysis flow.
- Insights and weekly review.
- Session prep export and share artifact.
- Safety plan and elevated/acute risk routing.
- Privacy, retention, notification, and voice settings.
- Offline capture for quick check-ins, diary entries, routine completion, and chain-analysis drafts.

### 3.2 Out of Scope for V1

- Therapist EHR, billing, or full clinician portal.
- Public social features.
- Medication advice.
- Trauma exposure workflows.
- Diagnosis or treatment claims.
- Wearable integrations.
- Advanced localization beyond data model readiness.

## 4. Stack Decisions

### 4.1 Frontend

- HTML5 pages and semantic elements.
- CSS with one project stylesheet, CSS custom properties, responsive media queries, and reduced-motion support.
- Vanilla JavaScript modules loaded by browser-native `<script type="module">`.
- No frontend framework.
- No client-side build requirement for initial slices.
- PWA manifest and service worker added only when the slice needs installability/offline behavior.

### 4.2 Backend

- Bun runtime.
- JavaScript modules.
- HTTP server implemented with `Bun.serve()` unless a later decision explicitly adopts a small router.
- PostgreSQL as the primary application database.
- SQL migrations stored in repo and run by a Bun script.
- Server-side OpenAI calls only from the Bun backend.
- Browser voice sessions must use short-lived Realtime client secrets generated by the backend. The primary API key must never reach the browser.

### 4.3 Testing

- Backend tests: `bun test`.
- Browser tests: Playwright through the repo-standard `playwright-cli` workflow.
- SQL verification: migration tests against a disposable local database or isolated schema.
- Accessibility checks: keyboard navigation, focus order, labels, color contrast, reduced-motion mode.
- Safety tests: deterministic fixtures for normal, elevated, and acute risk triggers.

- Server startup must validate required variables and fail fast with a clear error.
- Browser-visible config must be exposed through a safe `/api/config/public` route and must never include secrets.

## 8. Vertical Slice Methodology

Anchor must use walking skeleton and vertical slice development.

### 8.1 Pass 0: Walking Skeleton

Pass 0 must prove every required layer works with real code:

- Frontend: one HTML page loads in browser.
- CSS: minimal but real responsive styling.
- Client JavaScript: one `fetch()` call with success and error handling.
- Bun API: one route with structured error handling.
- PostgreSQL: one table and one seeded row.
- Browser verification: page renders real data from PostgreSQL.

Pass 0 done condition:

```text
Open browser -> load app -> client fetches Bun API -> API queries PostgreSQL -> response renders in page -> error state can be forced and displayed.
```

No agent may start Pass 1 until Pass 0 is confirmed in the browser.

### 8.2 Pass Rules

For every pass after Pass 0:

1. Name the user-visible capability first.
2. Touch only the layers needed for that capability.
3. Keep the system runnable at the end of the pass.
4. No orphan routes, tables, services, screens, or TODO stubs.
5. Write failing tests first, then implementation, then refactor.
6. Run browser tests before marking a user-facing pass complete.
7. Update the vertical-slice dashboard state.
8. Update the capability ledger in this spec or a dedicated implementation ledger.

## 9. Vertical Slice Dashboard Integration

`vertical-slice-dashboard.html` is a required project coordination tool. It stores progress in browser `localStorage` under key `vsd-v2` and supports JSON import/export.

### 9.1 Dashboard State Contract

The dashboard JSON shape is:

```json
{
  "projectName": "Anchor",
  "passes": [
    {
      "name": "Walking Skeleton",
      "note": "Prove all layers with one real end-to-end path"
    }
  ],
  "layers": [
    {
      "icon": "UI",
      "name": "Frontend",
      "tech": "HTML5 / CSS"
    }
  ],
  "tasks": [
    [
      {
        "description": "Task description for layer 0, pass 0.",
        "subtasks": ["Concrete verification step."]
      }
    ]
  ],
  "statuses": [
    ["todo"]
  ]
}
```

Dashboard invariants:

- `passes.length` defines the number of vertical slices.
- `layers.length` defines the number of tracked implementation layers.
- `tasks.length` must equal `layers.length`.
- Each `tasks[layerIndex].length` must equal `passes.length`.
- `statuses.length` must equal `layers.length`.
- Each `statuses[layerIndex].length` must equal `passes.length`.
- Valid status values are `todo`, `active`, and `done`.
- A pass is complete only when every layer cell in that pass is `done`.
- Legacy string tasks may be normalized into `{ "description": "...", "subtasks": [] }`.
- Import validation must reject files missing `passes`, `layers`, `tasks`, or `statuses`.
- Adding or deleting a pass must update every task row and every status row.
- Adding or deleting a layer must update the layer list, matching task row, and matching status row.

## 12. DBT Data Requirements

### 12.1 Quick Check-In

Required fields:

- `created_at`
- `primary_emotion_score` integer 0 to 5
- `primary_urge_score` integer 0 to 5
- `energy_state` enum: `low`, `medium`, `high`
- `anchor_context` enum: `morning`, `midday`, `evening`, `anytime`
- `suggested_next_action_status` enum: `accepted`, `dismissed`, `deferred`

Optional fields:

- `note` one sentence
- `location_context` enum: `home`, `work`, `school`, `commute`, `social`, `other`

### 12.2 Full Diary Card

Required stable fields:

- `entry_date`
- anchor completion state for morning, midday, evening
- emotion ratings 0 to 5: anxiety/fear, sadness, anger, shame, guilt, numbness, joy/calm
- urge ratings 0 to 5: self-harm, suicidality, substance use, binge/restrict/purge, isolate/avoid, quit/give-up, lash out
- target behavior occurrence: `none`, `urge_only`, `action_occurred`
- skills used
- overall day difficulty 0 to 5

Optional first-party fields:

- sleep duration
- sleep quality
- medication adherence
- free-text notes
- limited custom target fields

Custom field rule:

- Custom targets must be limited, typed, and mapped into the stable export schema.
- Custom fields must never break charts, weekly review, or session-prep packets.
- Analytics and clinician exports must rely on stable core fields even when optional fields are hidden.

### 12.3 Target Hierarchy

All tracked urges and behaviors must map to one DBT hierarchy level:

1. `life_threatening`
2. `therapy_interfering`
3. `quality_of_life_interfering`
4. `skills_generalization`

Reviews, safety handling, coaching recommendations, and clinician summaries must sort in that order.

### 12.4 Default V1 Target Mapping

Default life-threatening targets:

- `self_harm_urge`
- `self_harm_action`
- `suicidality_urge`
- `suicidality_plan_action`

Default therapy-interfering targets:

- `skipped_therapy`
- `skipped_diary_card`
- `repeated_skipped_anchors`

Default quality-of-life-interfering targets:

- `substance_use`
- `binge_restrict_purge`
- `isolate_avoid`
- `lash_out`
- `dissociation_shutdown`
- `quit_give_up`

Default skills/generalization targets:

- `used_skill`
- `completed_anchor`
- `completed_repair_action`

Mapping rules:

- Self-harm and suicidality targets always sort before other targets.
- Skipped diary card for 3 or more days and repeated anchor avoidance are therapy-interfering for review purposes.
- Session packets must include target hierarchy labels, not just flat behavior names.
- Seed data must include all default targets even if the user later hides some fields.

## 16. Safety System

Risk tiers:

- `normal`: no elevated signal; normal coaching allowed.
- `elevated`: concerning distress, passive death wish, uncertainty about safety, or rapidly rising self-harm urges without clear imminent plan.
- `acute`: imminent intent, current attempt, inability to stay safe, or time-bound plan with access to means.

Elevated flow:

1. Safety Guardian takes over.
2. UI enters Safety Mode.
3. App asks whether the user is safe right now with `yes`, `not sure`, `no`.
4. `yes` leads to grounding, simplified next action, optional return to normal coaching.
5. `not sure` keeps Safety Mode active and prompts support contact plus safety plan.
6. `no` escalates to acute mode.

Acute flow:

- Normal coaching locks for the session.
- Emergency and support actions are foregrounded.
- App surfaces U.S. resources including 988 and 911 for the initial locale.
- The app must not provide self-harm instructions or simulate crisis counseling.

Every elevated or acute interruption creates a `safety_events` record.

## 17. Privacy and Retention

Defaults:

- No advertising-based data use.
- Raw audio not retained after live session.
- Live transcript text not persisted by default.
- Voice metadata and redacted traces retained for 30 days unless policy shortens it.
- Saved transcript text, if opted into, retained for 30 days and deletable immediately.
- Session summaries promoted into diary, journal, or session prep become regular user data.
- Account deletion must delete product-side saved transcripts, derived summaries, and share artifacts within 30 days.

User controls:

- Export my data.
- Delete my data.
- Voice transcript retention toggle.
- Per-session Do Not Save control.
- Therapist sharing consent and revocation.
- Optional local app lock/passcode.
